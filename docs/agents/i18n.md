# Internationalization (i18n)

> Detail spec referenced from [AGENTS.md](../../AGENTS.md). Rules here are binding; they are not optional guidance.

## Internationalization (i18n) — Bilingual (বাংলা/English) Support

### Objective

প্রতিটি নতুন ফিচার, মডিউল, পেজ, কম্পোনেন্ট, ফর্ম, টেবিল, এবং API — **বাংলা ও ইংরেজি — উভয় ভাষায়** ব্যবহারকারীর কাছে উপস্থাপন করতে হবে। কোনো মডিউল শুধুমাত্র ইংরেজিতে তৈরি করে later localization-এর জন্য রেখে দেওয়া যাবে না। প্রতিটি ফিচার ডেলিভারির সময়ই সম্পূর্ণ bilingual হতে হবে।

### Technology Choice

This project does **not** use `next-intl`, path prefixes (`/en/...`, `/bn/...`) or per-module JSON files. The implemented system is a single typed translation object plus a Zustand store:

| Piece | Location |
|---|---|
| Translation data | `frontend/src/i18n/translations.ts` — one file, `export const translations = { en: {...}, bn: {...} }` |
| Runtime hooks | `frontend/src/i18n/useLanguage.ts` — Zustand store: `language`, `setLanguage()`, `t(path, params?)` |
| Persistence | Zustand `persist` → `localStorage` key `language-storage`, mirrored to cookie `lang` (1 year, `samesite=lax`) so the server can read it |
| Language switcher | `frontend/src/components/layout/LanguageSwitcher.tsx` — reuse it, never rebuild it |
| `<html lang>` sync | `frontend/src/components/layout/DynamicPageTitle.tsx` |

`t()` semantics (know these before debugging a string):

- Path is dot-separated into the nested object: `t('user.list.title')`.
- Missing key in the active language → falls back to `en`; missing in `en` too → returns the **key path itself** (`user.list.title` renders literally). Seeing a dotted path on screen means a key is missing, not a rendering bug.
- Placeholders use `{name}` and are replaced from the second argument: `t('common.selected', { count: 3 })`.

### Namespaces Inside `translations.ts`

There is no `messages/` directory. Namespaces are the **top-level keys** inside `translations.en` / `translations.bn`, and each page/section gets one:

```ts
export const translations = {
  en: {
    common: { save: "Save", cancel: "Cancel" },
    user: {
      list: { title: "User List", create: "Create User" },
      fields: { name: "Name", email: "Email" },
    },
  },
  bn: {
    common: { save: "সংরক্ষণ", cancel: "বাতিল" },
    user: {
      list: { title: "ব্যবহারকারী তালিকা", create: "নতুন ব্যবহারকারী" },
      fields: { name: "নাম", email: "ইমেইল" },
    },
  },
};
```

Both `en` and `bn` must carry the **same key paths** in the same file — a key added to one language and not the other is an incomplete change.


### Locale Detection & Routing

1. **No path-based localization** — routes are language-agnostic (`/users`, not `/en/users`). Locale lives in app state, not in the URL.
2. **Resolution order at runtime** — Zustand persist rehydrates `language` from `localStorage` (`language-storage`); `setLanguage` then mirrors it to the `lang` cookie so the server can read it. Default is `en`.
3. **Locale switching** — `LanguageSwitcher` in the header calls `setLanguage('bn' | 'en')`; no navigation, no route change, the tree re-renders and the cookie updates automatically.
4. **Document sync** — `DynamicPageTitle` sets `document.title` (bilingual) and `document.documentElement.lang` to `en`/`bn` on every route and language change.

Do not introduce a locale URL segment or middleware-based redirection; that contradicts the shipped implementation.

### Backend — Multilingual Data Storage

#### Static/Configuration Data

Translations for static data (module names, permission labels, dropdown options etc.) should be stored in JSON translation files on the frontend only.

#### Dynamic/User-Generated Data

If a module has fields that need to store content **in multiple languages** (e.g., product name in both languages, category description), follow this pattern:

```python
# Database model with multilingual support
class Product(Base):
    __tablename__ = "products"

    id = Column(Integer, primary_key=True)
    name_en = Column(String(200), nullable=False)   # English name
    name_bn = Column(String(200), nullable=False)   # Bengali name
    description_en = Column(Text, nullable=True)
    description_bn = Column(Text, nullable=True)
    ...
```

**Rules:**
- `name_en` এবং `name_bn` — উভয়ই required (যদি না business logic নির্দিষ্ট ভাষার জন্য optional করে)
- `description_en` / `description_bn` — nullable হতে পারে
- API response-এ `Accept-Language` header অনুযায়ী শুধুমাত্র প্রয়োজনীয় language field রিটার্ন করা, অথবা উভয় ভাষার data একসাথে রিটার্ন করে frontend-এ locale অনুযায়ী দেখানো
- Frontend ফর্মে উভয় ভাষার input field পাশাপাশি দেখানো (tab বা split-view-এ)

#### API Response Pattern for Multilingual Data

Option A — Locale-aware response:
```json
{
  "id": 1,
  "name": "Product Name in Requested Language",
  "description": "Description in Requested Language"
}
```

Option B — Full bilingual response (উভয় ভাষার data):
```json
{
  "id": 1,
  "name_en": "Product Name",
  "name_bn": "পণ্যের নাম",
  "description_en": "Description",
  "description_bn": "বিবরণ"
}
```

Choice between A and B depends on module requirements. Option B is preferred for forms/edit pages, Option A for display-only pages.

### Frontend Implementation Rules

#### 1. Import and Usage Pattern

```tsx
"use client";

import { useLanguage } from "@/i18n/useLanguage";

export default function UserList() {
  const { t } = useLanguage();

  return (
    <div>
      <h1>{t("user.list.title")}</h1>
      <Button>{t("user.list.create")}</Button>
    </div>
  );
}
```

Call `useLanguage()` once per component and reuse `t`. `t` is a plain function returning `string`, so it is safe to pass around, but it is not reactive by itself — the component must subscribe via the hook to re-render on language change.

#### 2. Dynamic Values in Translations

```json
{
  "user": {
    "messages": {
      "welcome": "Welcome, {name}!",
      "record_count": "{count} users found"
    }
  }
}
```

```tsx
t('messages.welcome', { name: 'John' });
t('messages.record_count', { count: users.length });
```

#### 3. Forms — Bilingual Input Fields

When creating/editing an entity that requires multilingual data:

- **Side-by-side layout:** দুটি input field পাশাপাশি দেখান — left side-এ English, right side-এ Bengali
- **Label pattern:** `Name (English)` / `নাম (বাংলা)`
- **Tab approach:** অথবা দুইটি tab ব্যবহার করুন — "English" এবং "বাংলা"
- **At least one required:** কমপক্ষে একটিতে value থাকতেই হবে (business logic অনুযায়ী)

```tsx
<div className="grid grid-cols-1 md:grid-cols-2 gap-4">
  <div>
    <Label>{t('fields.name')} (English)</Label>
    <Input {...register('name_en')} placeholder="Enter name in English" />
    {errors.name_en && <p className="text-red-500">{errors.name_en.message}</p>}
  </div>
  <div>
    <Label>{t('fields.name')} (বাংলা)</Label>
    <Input {...register('name_bn')} placeholder="বাংলায় নাম লিখুন" />
    {errors.name_bn && <p className="text-red-500">{errors.name_bn.message}</p>}
  </div>
</div>
```

#### 4. Validation Messages

- Frontend validation messages must come from translation files
- Backend validation errors are returned in English by default; frontend maps error codes to localized messages

```tsx
// translations.ts → bn.validation
{
  "validation": {
    "name_required": "নাম আবশ্যক",
    "email_invalid": "ইমেইল ঠিকানা সঠিক নয়"
  }
}
```

#### 5. Table Columns

Table headers should use translation keys. Data display should respect current locale:

```tsx
const columns = [
  { key: 'name', label: t('fields.name') },
  { key: 'email', label: t('fields.email') },
  { key: 'role', label: t('fields.role') },
  { key: 'status', label: t('fields.status') },
];
```

#### 6. Breadcrumbs & Navigation

```tsx
const breadcrumbs = [
  { label: t('list.title'), href: '/users' },
  { label: currentUser.name, href: `/users/${id}` },
];
```

#### 7. Language Switcher Component

`LanguageSwitcher` already exists — **reuse it, do not write another one**:

```tsx
// frontend/src/components/layout/LanguageSwitcher.tsx (existing)
const { language, setLanguage } = useLanguage();
setLanguage(lang.code); // 'en' | 'bn' — no router, no pathname change
```

It renders in the dashboard header/sidebar and is permission-free (every user can switch language).

### Rules for New Modules

১. প্রতিটি নতুন মডিউলের জন্য `translations.ts`-এ **আলাদা top-level namespace** তৈরি করতে হবে (যেমন `scratch_card_serials`, `ga_query`)
২. ওই একই `translations.ts` ফাইলে `en.<namespace>` এবং `bn.<namespace>` — **দুটি ব্লকই** যোগ করতে হবে, একই key path নিয়ে
৩. বাংলা অনুবাদ বাদ দিয়ে শুধুমাত্র ইংরেজি key যোগ করা যাবে না
৪. ন্যূনতম নিচের keys প্রতিটি মডিউলে থাকতে হবে:
   - `{module}.list.title`
   - `{module}.list.create`
   - `{module}.fields.*` (প্রতিটি DB field-এর জন্য)
   - `{module}.validation.*` (প্রয়োজনীয় validation messages)
   - `{module}.messages.create_success`
   - `{module}.messages.update_success`
   - `{module}.messages.delete_success`
   - `{module}.messages.delete_confirm`
   - `{module}.messages.no_data` (empty state)
   - `{module}.guide.*` — Page Guide content (`overview`, `features.*`, `steps.*`, `notes.*`)

### Form Error Display — Bilingual

```tsx
// Field-level error from the backend, localized via the translation store
const { language, t } = useLanguage();

{error?.fields?.email && (
  <p className="text-red-500 text-sm mt-1">
    {language === "bn"
      ? t(`errors.${error.error_code ?? "validation_error"}`)
      : error.fields.email}
  </p>
)}
```

Backend always returns errors in English. For `bn`, resolve `error.error_code` (or the field path) through `t()` so the message is translated; never hardcode Bengali strings in components.

### Backend — Multilingual Support for Error Messages

Backend JSON error responses should include an optional `error_code` field that frontend can use to look up the translated message:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "error_code": "email_already_exists",
    "message": "Email already exists",
    "fields": {
      "email": "Email already exists"
    }
  }
}
```

Frontend translation block:

```jsonc
// translations.ts → bn.errors
{
  "errors": {
    "email_already_exists": "এই ইমেইলটি ইতিমধ্যে ব্যবহার করা হচ্ছে"
  }
}
```

### Checklist — i18n

প্রতিটি নতুন মডিউল/ফিচারের জন্য:

- [ ] `translations.ts` → `en.<module>` key block যোগ করা হয়েছে
- [ ] `translations.ts` → `bn.<module>` — একই key path সহ বাংলা অনুবাদ যোগ করা হয়েছে
- [ ] All UI text goes through `useLanguage().t()`, no hardcoded English strings
- [ ] Form fields for multilingual data (name_en/name_bn) properly implemented
- [ ] Validation messages come from translation keys
- [ ] Backend error codes are mapped to `errors.*` keys
- [ ] Table headers use translated strings
- [ ] Breadcrumbs, page titles, buttons — all translated
- [ ] `LanguageSwitcher` (existing component) flips the page without navigation
- [ ] Empty states, loading states, error states — all translated
- [ ] Sidebar/menu labels — translated
- [ ] Notifications/toast messages — translated
- [ ] Pagination labels — translated
- [ ] Both languages checked by toggling `LanguageSwitcher` on the same route
- [ ] No dotted key path visible on screen (a visible `module.section.key` means a missing translation)
- [ ] `<html lang>` flips between `en` and `bn` (verify in DevTools)
- [ ] RTL (Right-to-Left) layout check — বাংলা টেক্সটের জন্য কোনো RTL adjustment প্রয়োজন কিনা নিশ্চিত করা হয়েছে
